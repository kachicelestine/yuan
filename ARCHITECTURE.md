# Architecture

Lychee is a modular monolith: one Next.js app, split inside into bounded contexts that each follow clean architecture. This file records the decisions and the rules that keep them true. Add a new entry under "Decisions" when one changes. The research behind the product and the path from a free single server to multi-region scale is in [docs/research](docs/research/README.md).

## Layout

```
src/
  app/                 Next.js routes, layouts, route handlers          (presentation)
  components/          React UI                                         (presentation)
  server/              composition root: wiring, cached queries, server actions
  modules/<context>/
    domain/            entities, value objects, domain events, repository interfaces
    application/       use cases (commands and queries), ports for outside services
    infrastructure/    Drizzle schema and repositories, adapters for ports, seeds
    index.ts           the module's public surface
  shared/
    kernel/            domain building blocks used by every module (Result, Money, Id…)
    infrastructure/    database client, migration runner
  config/              validated environment and brand
  fixtures/            design-phase sample data, now used only to seed the database
  lib/                 client-side helpers from the design phase, shrinking over time
drizzle/               generated SQL migrations (committed)
scripts/               database and data tooling, run with tsx
```

## The dependency rule

Dependencies point inward: presentation → server → application → domain. ESLint enforces it (`eslint.config.mjs`, "Architecture boundaries").

- **Domain** imports nothing outside `shared/kernel` and its own module. No Next.js, React, Drizzle, Zod or I/O.
- **Application** imports its own domain and the kernel. It reaches the outside world only through interfaces (ports) it defines.
- **Infrastructure** implements those interfaces with Drizzle, HTTP clients and chain RPC.
- **Presentation** never imports a module's domain or infrastructure. Server code calls use cases through `src/server`; client components receive plain data as props or call server actions.
- Modules talk to each other only through `index.ts`, never by reaching into another module's folders.

## Bounded contexts

| Context | Owns |
|---|---|
| markets | Countries (all of ISO 3166), currencies, time zones, exchange rates, tax and shipping defaults |
| catalog | Categories, sellers and storefronts, products (options, tiers, specs), search |
| content | Videos, notes, reviews, questions: the social layer that sells products |
| identity | Accounts, sessions, sign-in (email code, wallet, Google, Apple) |
| ordering | Carts, checkout, orders and their journey, Protect (escrow) cases |
| payments | Stablecoin invoices, on-chain confirmation, the escrow ledger, seller payouts |
| engagement | Coupons, coins, polls, chops, drops, reminders, rankings |
| live | Live rooms, schedule, chat |

## Decisions

1. **Modular monolith, not microservices.** One deployable keeps a small team fast; the module boundaries make a later split possible without a rewrite.
2. **PostgreSQL with Drizzle ORM.** Each context gets its own Postgres schema (`markets`, `catalog`, …), so ownership is visible in the database too. Migrations are generated by drizzle-kit into `drizzle/` and committed.
3. **Zero-setup local database.** Without `DATABASE_URL`, development uses embedded Postgres (PGlite) stored in `.data/pglite`, migrated and seeded on first use. Builds and tests use a fresh in-memory copy. Production requires `DATABASE_URL`. Only one process may open `.data/pglite`: `next dev` runs `generateStaticParams` in short-lived worker processes, and those get their own seeded in-memory copy.
4. **Identifiers are UUIDv7**, generated in the domain, so entities have identity before they are saved and ids sort by creation time.
5. **Money is integer cents of US dollars.** Buyers pay in dollar stablecoins, so USD is the unit of account everywhere. Local currencies are display-only, converted with stored exchange rates.
6. **Expected failures are values.** Use cases return `Result<T, DomainError>`; exceptions are for bugs and outages. Inputs are validated with Zod at the edge (server actions, route handlers, environment).
7. **Reads are cached, writes invalidate.** Public catalog queries use `"use cache"` with `cacheLife` and `cacheTag`; mutations call `revalidateTag`/`updateTag`. Per-user data streams behind `<Suspense>`.
8. **Payments are stablecoins, globally.** USDC and USDT on Base, Solana and Tron. A `PaymentGateway` port hides the network: the simulated adapter confirms invoices in development; the on-chain adapters match transfers to invoices by a unique amount (EVM, Tron) or a reference key (Solana). Buyer funds sit in the platform treasury and are tracked in a double-entry ledger: held per order (Protect), released to the seller's balance after delivery, paid out on request.
9. **Domain events go through an outbox.** Use cases record events (`OrderPlaced`, `OrderPaid`, `OrderCancelled`, `InvoicePaid`, `InvoiceExpired`) through the kernel's `EventLog` port, which writes them to `platform.outbox` in the same transaction as the change: an event is never lost when the change commits, never sent when it rolls back. A dispatcher delivers them at least once (leases with `FOR UPDATE SKIP LOCKED`, exponential backoff, failed rows kept), so handlers must be idempotent. Recurring jobs (invoice sweep every 30 s, exchange rates daily, pruning) are claimed through `platform.schedules`, so each runs once however many instances tick. Jobs run inside the web server (`JOBS=inline`, one server) or in `pnpm worker` / the `worker` container (`JOBS=off`).
10. **Tests.** Vitest. Domain and use cases get fast unit tests with in-memory fakes; repositories get integration tests against in-memory PGlite, using the same migrations as production. Integration tests call the real composition root (`wire` in `src/server/container.ts`) with a fixed clock, so they test the wiring that ships.
11. **The account is the source of truth; the device mirrors it.** Signed out, the bag, lists and claimed coupons live in the browser. `GET /api/account` returns the account's copy; the first time a device sees an account it merges its own copy in (`syncAccountAction`, mode `merge`), and later edits are saved a moment after they stop (mode `save`). Edits made offline are flagged and saved on the next visit. Signing out removes the account's data from the device. Anything with value (coins, coupons bought with coins) changes only through its own server action and is never accepted from a device.
12. **Coupons are reserved, then spent.** Checkout reserves the coupon in the same transaction as the order (a conditional update, so two checkouts can't share one); payment spends it; an invoice that expires unpaid cancels the order and returns the coupon.
13. **Performance budget: first paint and largest paint within 1 s on a mid-range phone on 4G.** Measured cold (empty browser cache) with headless Chrome at Fast 4G and a 4x slower CPU. What gets us there, each choice measured before it stayed:
    - *CSS is inlined* (`experimental.inlineCss`): Tailwind's CSS is small, and no render-blocking stylesheet request means first paint as soon as the HTML is parsed.
    - *Photos come from our own origin.* The `/img` route (`src/app/img/[photo]/route.ts`) fetches each exact rendition from Unsplash's CDN once, keeps it in memory and on disk, and serves it immutable for a year; a CDN in front of the app caches it at the edge. Phones never open a second connection, which costs about 0.6 s on a slow network. Next's built-in optimizer was tried and dropped: it pulls each full-size original first (0.5–1 MB), which timed out on slow links.
    - *Images are sized for what's on screen.* Widths stop at 1080; quality drops as width grows; grid and list images are capped at 2x density on 3x phones (`capDensity`); cards ask the CDN for their own crop (`reframe`). Only the hero gets `fetchPriority="high"`, and feed slides load their photo only when one swipe away.
    - *Less JavaScript.* No zod in the browser (the public env is checked by hand); the command palette loads on first use; countries travel as tuples, not objects. The React Compiler was tried and left off: it made every page's JS 10–15% larger.
    - *Judge speed in production mode* (`pnpm preview`): `next dev` compiles on demand and is several times slower.

14. **Deployment is a plain Node server in Docker.** `next build` with `output: "standalone"` (Dockerfile), plus esbuild-bundled `ops/migrate.mjs`, `ops/seed.mjs` and `ops/worker.mjs`. Stage 0 runs one Oracle Always Free ARM server behind a Cloudflare Tunnel (no inbound web ports), Postgres 18 in Compose, nightly dumps to R2 ([deploy/README.md](deploy/README.md)). Every build gets a `NEXT_DEPLOYMENT_ID` (version-skew protection) and the same `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`; `/api/health` gates deploys; a post-deploy call to `/api/internal/revalidate` (bearer `INTERNAL_TOKEN`) refreshes data prerendered against the build's empty database. A real deployment refuses simulated payments and on-screen sign-in codes unless `DEMO_DEPLOYMENT=true`.
15. **The feed is one ranked order, cut into pages.** Content ranks every published video (engagement per view smoothed toward a typical rate, times a freshness curve, with every fourth slot given to the newest video that has few views yet) and caches the order for a minute. `GET /api/feed?offset=` cuts pages from it and joins each video with its products and shop from the catalog (`src/server/feed.ts`), so the order is shared and cacheable while the device tunes what's ahead with the viewer's "more / less like this". Counters (likes, comments, shares, views) live in `content.video_stats`, apart from the video row, and may lag a few minutes in cached pages; a person's own likes come from `GET /api/me/likes`, never from a cached page. Each like or vote is one row per person (`content.likes`) written in the same transaction as its counter. Watching is reported by `sendBeacon` to `POST /api/events`, summed in memory per video and flushed every 5 s in one statement, so a busy feed costs a few writes a second, not one per swipe; a crash loses at most one window of view counts.
16. **Uploads go straight to storage; encoding is its own queue.** An `ObjectStorage` port (kernel) has two adapters: Cloudflare R2 through its S3 API (production: presigned PUTs whose signature covers the content type and exact length, files served from the bucket's own domain with no egress fees) and the local disk (development and demos: `PUT /api/media/upload` with an HMAC ticket, `GET /media/...` with byte ranges). Browsers never send video through the app server. Publishing an upload saves the video as `processing`; the background jobs' third loop claims the oldest one with a lease on the video row (`FOR UPDATE SKIP LOCKED`, 15 minutes, 3 attempts), so a long encode never delays outbox delivery or recurring jobs, and two workers never encode the same video. The `VideoEncoder` port has an ffmpeg adapter (in the Docker image: H.264/AAC MP4 at 720p and 480p by the short side, never upscaled, `+faststart`, a JPEG poster, brightness for the glass tone) and a copy adapter for machines without ffmpeg. Progressive MP4 rather than HLS keeps the player a plain `<video>`, with no streaming library to download. Where uploads are pre-moderated (production default) an encoded video waits in `review`; going live records `VideoPublished`, whose handler refreshes the feed, shop and category caches.

## Status

Built: markets, catalog (with search), identity, ordering (with the server-side bag), payments, and the account side of engagement (coupon wallet, coins, check-ins, saved items, alerts, watches). Not yet: content, the rest of engagement (missions, badges, polls, chops, drops, rankings), live. Screens for unbuilt contexts still read `src/fixtures` through `src/lib`, and say so in a comment where they do.

## Risks to settle before launch

- **Abuse limits.** Sign-in codes are limited per email and per code, and sign-in, checkout, account writes and search are limited per IP or account in `platform.rate_limits` (`src/server/rate-limits.ts`). The client IP comes only from the trusted proxy's header (`TRUST_PROXY`). High-volume paths (photos, static assets) are left to Cloudflare's rules. The `/img` route only serves Unsplash photos at the app's own sizes and qualities, but any Unsplash photo id; once sellers upload media it should serve our own storage only.

- **Crypto licensing.** Taking stablecoin payments and holding them in escrow can require money-transmitter or virtual-asset licences, KYC/AML checks and Travel Rule compliance, depending on the country. Some countries restrict paying for goods with crypto.
- **Mainland China.** Crypto transactions are banned there, so paying sellers based in mainland China in stablecoins carries legal risk. The payout port is designed so a regulated fiat off-ramp (or a Hong Kong entity) can be plugged in for those sellers.
- **Reaching China.** Vercel has no servers in mainland China and its domains can be slowed or blocked. Seller tools may need a route that reaches China reliably, or an ICP-licensed mirror.
